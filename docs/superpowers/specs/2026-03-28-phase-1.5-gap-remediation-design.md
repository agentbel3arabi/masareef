# Phase 1.5: Gap Remediation & Polish — Design Spec

**Date:** 2026-03-28
**Status:** Approved
**Scope:** Full remediation of Phase 1 gaps — infrastructure upgrades, backend completeness, UI foundation, page fidelity, landing page, and workflow formalization

---

## 1. Context & Motivation

Phase 1 (Foundation) is functionally complete: accounts, transactions, transfers, categories, auth, i18n, dark mode, and integration tests are shipped (Units 1A–1J, PRs #4–#15). However, a gap analysis revealed six workstreams of unfinished or missing work that must be addressed before Phase 2 (Import & Templates) begins:

1. **Landing page** — Stitch design exists, no spec or implementation
2. **UI design fidelity** — Current pages don't match Stitch designs (simpler layout, missing visual elements)
3. **Phase 1 feature completeness** — Credit card billing fields, bulk operations, advanced filters, account edit, net-worth endpoint
4. **Infrastructure upgrades** — Next.js 16 + Tailwind v4 + shadcn base-nova migration (already planned in `docs/superpowers/plans/upgrade/`)
5. **Workflow process** — No formalized unit execution → code review → UAT → acceptance pipeline
6. **Cross-phase documentation gaps** — Category hierarchy and icons (addressed here); APScheduler, rate limiting, error handling (deferred to roadmap)

## 2. Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Scope | Full remediation spec (all 6 workstreams) | Ship a complete Phase 1.5 before Phase 2 |
| Upgrade timing | PR1 + PR2 first, then all other work | Avoids double-work — UI components built once on final stack |
| Landing page | Full marketing page (hero, pricing, testimonials) | Stitch design 01 is complete; implement it fully |
| UAT process | Phase-specific checklists from success/acceptance criteria | Each unit gets custom UAT derived from feature specs |
| UI fidelity | Functional fidelity — similar or better than Stitch | Use shadcn/ui patterns, design tokens win, but result must never look like a visual downgrade |
| Credit card depth | Fields + visual indicators now | Full statement cycle (statement date, min payment, statement vs current balance) deferred to roadmap |
| Category enhancements | Hierarchy + icons in Phase 1.5 | Categories are core Phase 1; improving them now strengthens everything built on top |
| Screen scope | All Phase 1 screens to full Stitch fidelity + onboarding + empty states | Comprehensive polish pass |

## 3. Wave Structure

Phase 1.5 is organized into 5 sequential waves, each containing 2–3 units. Every unit follows the formalized workflow: Plan → Execute → Copilot Review → Fix → UAT → Fix → Merge.

## 5. Wave 2: Backend Completeness

### Unit 1.5C: Account Enhancements

**Account edit endpoint:**
- `PUT /api/v1/accounts/{id}` — mutable fields: `name`, `institution`, `credit_limit`, `billing_cycle_day`, `payment_due_day`
- Immutable fields: `currency`, `type` (return 422 if attempted)
- Validation: `credit_limit` required when `type IN (credit_card, financing_app)`
- Validation: `billing_cycle_day` and `payment_due_day` only accepted for `credit_card` and `financing_app` types

**Net-worth endpoint:**
- `GET /api/v1/accounts/net-worth`
- Response: `{ data: { by_currency: { "EGP": 50000000, "USD": 100000 }, total_base_minor: 52000000, base_currency: "USD", account_count: 7 } }`
- Aggregates `displayed_balance_minor` for all active accounts
- Converts to base currency via USD hub exchange rates
- Base currency comes from household settings (default: USD). **Note:** If `household.base_currency` column doesn't exist yet, add it via migration in this unit (VARCHAR(3), default "USD")

**Credit card validation tightening:**
- Enforce `credit_limit >= 0` (cannot be negative)
- Enforce `1 <= billing_cycle_day <= 31` and `1 <= payment_due_day <= 31` at schema level (Pydantic)
- Return descriptive validation errors for invalid combinations

**Acceptance criteria:**
- [ ] Account edit updates mutable fields correctly
- [ ] Account edit rejects immutable field changes with 422
- [ ] Net-worth endpoint returns correct multi-currency aggregation
- [ ] Credit card validation enforced
- [ ] Integration tests cover all new endpoints
- [ ] CI green

### Unit 1.5D: Transaction Advanced Filters + Bulk Operations

**Advanced filtering (7 dimensions):**
Extend `GET /api/v1/transactions` query params:
- `q` (existing) — full-text search on description
- `type` (existing) — `debit` or `credit`
- `date_from`, `date_to` (existing) — ISO date range
- `category_id` (NEW) — filter by category (accepts parent category ID to include children if hierarchy exists)
- `account_id` (NEW) — filter by specific account
- `amount_min`, `amount_max` (NEW) — filter by absolute amount range (in minor units)

All filters composable — multiple filters applied with AND logic.

**Bulk delete:**
- `POST /api/v1/transactions/bulk-delete`
- Request: `{ transaction_ids: [uuid, uuid, ...] }`
- Behavior: Soft-delete all listed transactions. Reverse balance impacts atomically. Validate all transactions belong to current household
- Response: `{ data: { deleted_count: N } }`
- Limit: Max 100 transactions per request

**Bulk re-categorize:**
- `POST /api/v1/transactions/bulk-categorize`
- Request: `{ transaction_ids: [uuid, ...], category_id: uuid }`
- Behavior: Update category_id on all listed transactions. Validate category belongs to household. Validate category type matches transaction type
- Response: `{ data: { updated_count: N } }`
- Limit: Max 100 transactions per request

**Acceptance criteria:**
- [ ] All 7 filter dimensions work individually
- [ ] Filters compose correctly (e.g., category + date range + amount range)
- [ ] `category_id` filter includes child categories when parent is specified
- [ ] Bulk delete soft-deletes and reverses balances atomically
- [ ] Bulk re-categorize validates type compatibility
- [ ] Edge cases: empty list returns 400, IDs from other household returns 403
- [ ] Integration tests cover filter combinations and bulk ops
- [ ] CI green

### Unit 1.5E: Category Hierarchy + Icons

- Predefined categories become top-level parents (cannot be made children)

## 6. Wave 3: UI Foundation

### Unit 1.5F: Error Boundaries + Toast Notifications + Loading Skeletons

**Error boundary:**
- Global `ErrorBoundary` component wrapping `(app)/layout.tsx`
- Catches React render errors, shows friendly bilingual fallback
- Fallback includes: error icon, "Something went wrong" message, "Try Again" button (calls `reset()`), "Go Home" link
- Does NOT catch async/API errors (those go through toast system)

**Toast notification system:**
- Integrate shadcn `Sonner` toast component (or equivalent from base-nova)
- Add `<Toaster />` to root layout
- Create `useApiMutation` wrapper hook that:
  - Shows success toast on mutation success ("Account created", "Transaction deleted", etc.)
  - Shows error toast on mutation failure (extracts `error.message` from API response envelope)
  - Replaces all existing bare `mutateAsync` calls with this hook
- Toast messages are i18n keys (bilingual)

**Loading skeletons:**
- `AccountCardSkeleton` — matches `AccountCard` dimensions with pulse animation
- `TransactionRowSkeleton` — matches table row dimensions
- `PageHeaderSkeleton` — title + action button placeholder
- `FilterBarSkeleton` — horizontal bar with input placeholders
- Apply skeletons to all pages during `isLoading` state (replace current blank/text loading states)

**API client error handling:**
- Centralize error parsing in `api-client.ts`
- Extract `{ error: { code, message, details } }` from API responses
- Throw typed `ApiError` class with code, message, status
- All hooks use `ApiError` for error handling

**Acceptance criteria:**
- [ ] Intentional render error shows error boundary (not white screen)
- [ ] All mutations show success/error toasts
- [ ] All pages show skeletons during initial load
- [ ] API errors surface user-friendly messages
- [ ] Bilingual toast messages work in Arabic and English
- [ ] CI green

## 9. Cross-Cutting Concerns

### Stitch Design Reference Rule
Every frontend unit (Wave 3–5) MUST:
1. Load the matching Stitch HTML file(s) from `docs/stitch-designs/html/`
2. Load `docs/guides/09-design-tokens.md`
3. When Stitch HTML conflicts with design tokens, **tokens always win**
4. The result must look **similar or better** than the Stitch design — never a visual downgrade
5. Use `docs/stitch-screen-map.md` for screen-to-page mapping

### UAT Process
Every unit follows the formalized workflow from Unit 1.5M. Each unit's implementation plan includes a derived UAT checklist with:
- 5 standard checks (CI, console errors, RTL, dark mode, mobile)
- Phase-specific checks derived from the unit's acceptance criteria
- User sign-off required before merge

### Branch Naming
All Phase 1.5 branches follow: `feature/1.5{letter}-short-slug`
Examples: `feature/1.5A-nextjs16`, `feature/1.5E-category-hierarchy`, `feature/1.5L-landing-page`
